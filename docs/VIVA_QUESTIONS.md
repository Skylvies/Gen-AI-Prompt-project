# Viva questions and easy answers (35)

File names in brackets point to where the answer lives in the code.

## A. Idea and scope

**1. What problem does your project solve?**
The same LLM answers differently depending on how you phrase the request. The project tests several phrasings of one task, measures the answers, and recommends the best prompt instead of guessing.

**2. What is prompt engineering?**
Designing the text you send to an LLM (wording, examples, format, rules) to get better outputs without changing the model.

**3. What does "adaptive" mean in your title?**
Two things: the few-shot examples adapt to the detected task type (summarise, classify, explain, general), and the recommendation adapts to the user's weights (and can be re-scored instantly). It does *not* automatically rewrite prompts yet; that is future scope. (`prompt_generator.py`, `scoring.py`)

**4. What are your objectives?**
Generate prompt variants, call an LLM through a clean interface, evaluate with measurable metrics, combine them with weights, recommend the best prompt, and show it all on a dashboard with history and export.

**5. Who would use this?**
Students, developers and teams who want evidence for choosing one prompt style over another for a given task.

## B. Prompting techniques

**6. Name the six techniques and what each does.**
Direct (raw task), Role-based (expert persona), Few-shot (worked examples), Structured (fixed sections), Constraint-based (explicit rules like a word limit), Reasoning-oriented (think privately, show answer + short justification).

**7. What is few-shot prompting and why can it help?**
Giving the model a couple of solved examples first. It copies their style, length and format, so outputs are more predictable.

**8. Why do you not show the model's chain-of-thought?**
The reasoning prompt tells the model to think privately and output only the answer and a short justification. Hidden reasoning is not reliable evidence of how the model worked, and showing it makes answers long and costly.

**9. Why wrap the task in `<task>` tags?**
It separates the instructions from the user's text, which helps the model and makes it harder for text inside the task to be mistaken for instructions. The code also stops a task from closing the tag early. (`prompt_generator._clean`)

**10. Are prompts generated by an LLM?**
No. They are fixed templates, so the same task always gives the same prompts. That makes experiments reproducible and keeps costs down.

## C. Metrics and scoring

**11. List your metrics.**
Relevance, validity, reliability (hallucination-risk indicator), conciseness, token usage, cost, latency, and the overall weighted score.

**12. How do you measure relevance?**
If the user gives a reference answer: word overlap between response and reference (F2, which weights recall more). Otherwise: what fraction of the task's keywords appear in the response. It is a lexical proxy, not true understanding. (`evaluator.relevance_score`)

**13. What checks make up validity?**
Not empty, at least 5 words, not cut off, not a refusal/error, and, if the prompt demanded it, the right section labels or word limit. Validity is the percentage of checks passed.

**14. How does your hallucination indicator work, and can it detect hallucinations?**
It cannot detect them. It lowers a score when the answer contains numbers, names or links that were not in the task/reference, or over-confident words like "always". These are risk signals, so it can give false alarms and miss believable falsehoods. That is why the UI calls it a risk indicator. (`evaluator.reliability_score`)

**15. How is conciseness scored?**
Full marks up to a target word count, then a straight-line drop to zero at three times the target.

**16. Where do token counts, cost and latency come from?**
Real Mode: token counts come from the API's usage field, latency is a timer around the call, cost is tokens × price per million. Demo Mode: tokens are estimated (characters ÷ 4) and latency is simulated, and the UI marks them so.

**17. Why normalise tokens, cost and latency?**
They have different units and no natural 0–100 scale. Min-max normalisation inside one experiment turns "lower is better" into a 0–100 score: best variant 100, worst 0.

**18. Write the overall score formula.**
overall = Σ weightᵢ × scoreᵢ over seven metrics, with weights rescaled to add up to 1. (`scoring.score_variants`)

**19. How do you choose the recommended prompt? What about ties?**
Highest overall score wins. Ties go to higher relevance, then lower cost, then lower latency. The app also warns when the margin over the runner-up is under 2 points.

**20. Are the weights fixed?**
No. The user sets them with sliders for each run and can re-score later. Changing weights can change the winner, and a test proves it.

**21. Why is "best prompt" not a universal truth?**
It is best for this task, these measurements and these weights, from one run each. Another task, model or weighting can give a different winner.

## D. Demo Mode and LLM access

**22. What is Demo Mode and why did you build it?**
A rule-based simulator so the whole app works without an API key or cost (for marking, offline demos, tests). It knows no facts. It builds placeholder text from the task's keywords and follows formatting instructions in the prompt. (`providers/mock.py`)

**23. Does Demo Mode produce real experimental results?**
No. Its numbers show how the pipeline works, not how a real model behaves. That is why every screen and export labels it "simulated".

**24. What is the provider abstraction?**
An interface with one method, `generate(prompt, max_tokens)`. `MockProvider`, `OpenAICompatibleProvider` (Groq, OpenRouter, Ollama, ...) and the optional `AnthropicProvider` all implement it. To add another vendor you write one new class; nothing else changes. (`providers/base.py`)

**25. How do you keep the API key secure?**
It is read only from an environment variable (`LLM_API_KEY`) on the server, never stored in code, the database, logs or API responses, and never placed in the frontend. `.env` is git-ignored, only `.env.example` (with no key) is committed, a test scans the repo for key-shaped strings, and another checks that `/api/config` never leaks it. The app even ignores `ANTHROPIC_API_KEY` unless that provider is chosen explicitly.

**26. What if one API call fails?**
That variant is recorded as failed (error message, rank none) and excluded from ranking and normalisation; the other variants still complete. Error messages are sanitised. (`service._call_llm`)

**27. Why do you run the API calls in threads?**
Each call waits on the network. Running them in parallel cuts total time from the sum to roughly the slowest one. A limitation is that parallel load can slightly affect measured latency.

## E. Technology choices

**28. Why FastAPI?**
It is simple, fast, validates requests automatically using Pydantic models, and generates interactive API docs at `/docs`.

**29. What do SQLAlchemy and SQLite do here?**
SQLite is a file database needing no server. SQLAlchemy lets us define tables as Python classes (Experiment, VariantResult) and change the database through one `DATABASE_URL` setting.

**30. Why React, Vite, Tailwind and Recharts?**
React builds the dashboard from small components; Vite gives fast builds; Tailwind styles quickly and responsively; Recharts draws the bar and radar charts.

**31. What is CORS and why did you configure it?**
Browsers block a page from calling an API on a different domain unless the API allows it. In deployment the frontend (Vercel) and backend (Render) have different domains, so the backend's `CORS_ORIGINS` lists the frontend URL.

**32. How does the frontend talk to the backend?**
Through a REST API with JSON (`frontend/src/api.js`). In development Vite proxies `/api` to the backend; in production `VITE_API_URL` holds the backend address.

## F. Quality, deployment, limits

**33. How did you test the project?**
110 automated pytest tests: prompt templates, each metric with edge cases, scoring maths checked by hand, providers (the LLM provider against a fake HTTP server, so no network or key is needed), a repo-wide scan for leaked keys, and the full REST API on a temporary database. The frontend is verified by a production build; CI runs both.

**34. How is it deployed?**
Backend on Render (Python web service, `render.yaml`), frontend on Vercel (Vite build). The two are linked by `VITE_API_URL` and `CORS_ORIGINS`. Free-tier caveats: cold starts and non-persistent SQLite.

**35. What are the main limitations and what would you do next?**
Limitations: heuristic metrics (not semantic), single run per prompt (no confidence intervals), task-specific results, Demo Mode is a simulator, subjective weights. Next: embeddings or LLM-as-judge for relevance, repeated runs with statistics, automatic prompt search/mutation, benchmark datasets, more providers, user accounts and PostgreSQL.

### Bonus quick answers
* **Why min-max and not z-score?** Simpler to explain, and gives a clean 0–100 range for a handful of variants.
* **Why F2 and not F1?** Covering the reference matters more than avoiding extra words.
* **Why a non-reasoning model as the default?** Models that "think" add hidden tokens and latency that have nothing to do with the prompt, which adds noise to the comparison.
* **Why the same temperature for every variant?** So differences in the answers come from the prompt, not from random sampling settings.
* **Why a free open-source model by default?** Anyone can run the project without paying, and the shared key can be a free one. The code also works with a model running locally (Ollama) with no key at all.
* **Where would you add a new metric?** Compute it in `evaluator.py`, add its key to `METRIC_KEYS`/`DEFAULT_WEIGHTS` in `config.py`, and add a column in `models.py` and the UI.
* **Is the CSV export safe to open in Excel?** Yes; cells starting with `= + - @` are prefixed with `'` to stop formula injection.
